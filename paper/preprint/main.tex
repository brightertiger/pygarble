\begin{abstract}
Text that reaches a language model, a survey database or a training corpus
is not always text. Keyboard mashing, random strings and placeholder
answers are common, and the usual detectors for them are either trained
classifiers with model downloads or hand-written rules that are rarely
measured. pygarble is a Python library with no runtime dependencies that
screens text with \nstrategies{} rule-based and statistical strategies
combined into named profiles. We evaluate it on two public datasets: a
Kaggle collection of \nA{} free-text survey responses labelled as junk,
and a Hugging Face collection of \nB{} English rows that pairs \nBpos{}
random strings with \nBneg{} tweets. Two CPU baselines are run under the
same conditions, a character Markov-chain gibberish detector and a
language identifier, with every method at its own default decision. The
\code{english\_fusion} profile captures \respct{english_fusion}{A_capture}\,\%
of the survey junk and recalls \respct{english_fusion}{B_recall}\,\% of the
random strings at a precision of \res{english_fusion}{B_precision}, from a
\mb{english_fusion}\,MB install that processes a thousand short texts in
\ms{english_fusion}\,ms. The Markov baseline flags fewer tweets but misses
more junk; the language identifier captures the most junk at the highest
install cost. A post hoc variant of the default profile that drops its two
encoding-damage checks shows that the ensemble adapts to a domain by
removing strategies: its false-positive rate on tweets falls from
\respct{english}{B_fpr}\,\% to \respct{english_tuned}{B_fpr}\,\% with no
change in recall. Code, per-row predictions and a verification script are
released so that every number can be recomputed.
\end{abstract}

\section{Introduction}

Free-text fields collect junk. Respondents mash the keyboard to reach the
next page of a survey, bots submit random strings to sign-up forms, and
scraped text carries encoding damage. Each of these costs something
downstream: a coder reads it, a model is trained on it, or an analysis
counts it as an answer. The problem has become more visible with large
language models (LLMs), where unreadable input wastes tokens, degrades
retrieval, and in guardrail settings is itself a signal that something
upstream has gone wrong. The author's own motivation for pygarble is
exactly this guardrail role: a cheap, local check that runs on every
prompt and every model output before anything more expensive does.

Two families of tools exist for the task. Trained classifiers, such as
the DistilBERT gibberish model used in open-source LLM guardrail
frameworks~\citep{madhurjindal}, are accurate on the distribution they
were trained on but need a model download and a deep-learning runtime,
and their decisions are hard to explain row by row. Rule-based detectors,
from character Markov models~\citep{gibberishdetector} to the nonsense
evaluator Nostril~\citep{hucka2018nostril} and the quality heuristics used
to filter web corpora~\citep{rae2021gopher,raffel2020t5}, are cheap,
local and explainable, and are often the first filter a team writes by
hand. What is rarely reported is how much junk such rules actually catch
on real data, and how much good text they wrongly flag.

This paper measures one such library. pygarble~\citep{pygarble} packages
\nstrategies{} strategies, each a function from a string to a score in
$[0,1]$, together with voting rules that combine them into profiles. It
has no runtime dependencies and ships its English reference tables inside
the wheel. We ask a plain question: at default settings, on data that
played no part in setting its defaults, how much junk does it capture, how much legitimate text
does it flag, and what does it cost compared with two common
alternatives?

The contributions are:
\begin{itemize}\setlength{\itemsep}{1pt}
\item A benchmark on two public datasets of short text, one of real
  human junk from survey research and one of random strings against
  tweets, with a frozen protocol, saved per-row predictions and a script
  that recomputes every reported number.
\item A comparison of pygarble's default and \code{english\_fusion}
  profiles with a character Markov-chain detector and a language
  identifier, all at their default decisions, on capture rate, precision,
  recall, false-positive rate, speed and install size.
\item A post hoc, domain-specific tuning of the default profile, reported
  separately from the main results, showing how the ensemble is adapted by
  removing strategies.
\item A description of pygarble's strategy families and profiles, with
  the full strategy list in the appendix.
\end{itemize}

\section{pygarble}
\label{sec:pygarble}

pygarble targets Python 3.8 and later and has no runtime dependencies.
The installed package, including its embedded English tables, is
\mb{english_fusion}\,MB. Besides gibberish detection it scans text for
secrets, personal data and profanity and can redact them; those features
are outside this paper.

\subsection{Strategies}

A \emph{strategy} is a function from a string to a score in $[0,1]$ and a
binary decision, with a flag that says whether the strategy applies to
the input at all. A strategy that needs letters or a minimum amount of
text, such as the Markov chain or cross parsing, reports that it does not
apply when the input has too little of either, rather than returning a
low score, so that absence of evidence is not counted as evidence that
the text is clean. The \nstrategies{} strategies fall into six families
(Table~\ref{tab:families}; the full list with one-line descriptions is in
Appendix~\ref{app:strategies}).

\begin{table}[t]
\centering

\label{tab:families}

\end{table}

\paragraph{Character statistics} measure properties of the character
stream that English rarely violates: the vowel ratio, Shannon entropy,
the longest consonant run, the letter-frequency profile, the symbol
share, and whether tokens are pronounceable.

\paragraph{English character models} compare the text with tables
learned from English: a character Markov chain over novel tokens, bigram
and trigram probabilities, a rare-trigram count, and a log-likelihood
ratio of English against a uniform reference.

\paragraph{Word-level checks} look words up in an embedded dictionary
and measure the unknown fraction, the fraction of anomalous tokens, the
density of English function words, the presence of English affixes, the
plausibility of adjacent word pairs, and whether the word-frequency
profile conforms to Zipf's law.

\paragraph{Structure and pattern checks} target forms of junk that are
not statistical: repeated substrings, keyboard-row walks and adjacent-key
sequences, hexadecimal strings, built-in patterns such as a letter
repeated four or more times or a five-key keyboard-row walk (with
optional user-supplied patterns), and local anomalies inside otherwise
ordinary text.

\paragraph{Encoding and script checks} fire on damage rather than on
meaning: mojibake byte signatures left by a wrong decoding, control
characters, and mixed or confusable Unicode scripts.

\paragraph{English-reference window statistics} compare a window of the
text with frequent English rather than applying a hand-written rule:
cross parsing, primed compression, $n$-gram rank and a permutation test.
Each statistic is measured against synthetic English of the same length,
and a score of 0.5 sits beyond the 99th percentile of that reference.

\subsection{Ensembles, voting and profiles}

\code{EnsembleDetector} runs a list of strategies and combines them
under a voting rule. With \code{any} voting, one applicable member
firing flags the text; \code{all}, \code{majority}, \code{average} and
\code{weighted} voting behave as their names say. \code{fisher} voting
treats each member's score as a test statistic: a table shipped with the
package records what that member scores on synthetic English word salads
of 8 to 480 characters, the member's $p$-value is the smallest tail
probability whose threshold the score exceeds, and the $p$-values are
combined with Fisher's method~\citep{fisher1925}. The combined $p$-value is mapped to a score so that the default
threshold of 0.5 flags a combined $p$-value of 0.001 or less. Named member
lists are called \emph{profiles}; Appendix~\ref{app:profiles} lists all
seven. Two are measured here:

\begin{itemize}\setlength{\itemsep}{1pt}
\item \code{english}, the default: Markov chain, log-likelihood ratio,
  word anomaly, mojibake, keyboard adjacency and control characters,
  under \code{any} voting. One member firing is enough.
\item \code{english\_fusion}, opt-in: word lookup, log-likelihood ratio
  and cross parsing under \code{fisher} voting. Each member's $p$-value is
  floored at 0.001, so when two or more members apply, at least two must
  score beyond their null thresholds before a text is flagged; one member
  decides alone only when it is the only one that applies.
\end{itemize}

A user can also pass any list of strategies, which is how the tuned
variant in Section~\ref{sec:tuning} is built. The English profiles score
English plausibility; they are not language identifiers, and meaningful
text in other Latin-script languages can be flagged. Scores are heuristic,
not calibrated probabilities.

\section{Datasets}
\label{sec:data}

\subsection{\SJ}

The Kaggle dataset \emph{Gibberish Text Classification}~\citep{dataA}
was compiled by a market-research practitioner from free-text responses
of poor-quality survey respondents. Its junk file holds \nArows{} rows,
every one labelled as junk; despite its \code{.xls} extension it is a
Windows-1252 CSV. We strip each response, drop empty rows and drop exact
duplicates, leaving \nA{} rows. Typical rows are keyboard mashes such as
runs of adjacent keys, repeated letters, and letters mixed with digits.
The median response is eleven characters long and most are a single token.

Because the file has no clean rows, the only metric on this dataset is
the \emph{capture rate}: the share of rows a method flags. The licence is
listed as unknown on Kaggle, so the repository stores row indices and
hashes, never the text.

\subsection{\TRS}

The Hugging Face dataset \emph{gibberish\_multilingual}~\citep{dataB}
(Apache-2.0) pairs random character strings with social-media posts in
seven languages. We pool its train, validation and test files and keep
the \nB{} non-empty rows whose language field is English: \nBpos{}
random strings, labelled junk, and \nBneg{} tweets, labelled clean.
Labels are used exactly as given and duplicates are kept (\nBdup{} rows
repeat an earlier text). The random strings are lower-case letter
sequences such as \code{edkylxhboa}; the tweets carry hashtags, handles
and, in \mojibakepct\,\% of cases, mojibake byte signatures from a
UTF-8 emoji decoded as Latin-1. The dataset labels those tweets clean
because it was built to separate random strings from posts.

On this dataset we report precision, recall and the false-positive rate
(FPR), the share of tweets flagged.

\section{Experimental setup}
\label{sec:setup}

\paragraph{Methods.} pygarble 0.11.0 is used with its defaults frozen at
commit \code{e3135ed}; no default or threshold was changed after any
result was seen. Two baselines run on CPU with pinned versions:
\begin{itemize}\setlength{\itemsep}{1pt}
\item \textbf{gibberish-detector} 0.1.1~\citep{gibberishdetector}, a
  character Markov model and the most downloaded gibberish detector on
  PyPI (about 230,000 downloads in the month to October 2026). The package ships no model, so one is trained with its own
  trainer on the corpus its README uses, and a text is flagged when its
  score exceeds the command-line default of 4.0.
\item \textbf{lingua} 2.2.0~\citep{lingua}, a language identifier, under
  the policy ``not detected as English is junk''.
\end{itemize}
There are no neural baselines; the DistilBERT gibberish model was
excluded to keep the comparison to tools that run with no model download.

\paragraph{Decisions.} Every method is scored at its own default
decision, the binary output it gives with default settings. No threshold
is fitted on either dataset.

\paragraph{Intervals.} Uncertainty is given as 95\,\% percentile
intervals from \resamples{} bootstrap resamples of rows, drawn with a
fixed seed and shared by all methods.

\paragraph{Pilot and protocol changes.} Before the protocol was written,
both datasets were scored once with pygarble's defaults to judge
feasibility. The \code{english\_fusion} numbers from that pilot equal the
ones reported here, because nothing in the package changed afterwards.
The first version of the protocol also fitted thresholds at fixed
false-positive rates on a development split of the tweets dataset and
compared more baselines and pygarble configurations; both were computed
and then removed from the paper's scope (Section~\ref{sec:limitations}).
The tuned variant in Section~\ref{sec:tuning} was added after the results
were seen and is reported as post hoc.

\paragraph{Environment.} All runs are single-threaded on an \cpuname{}
with Python \pyversion{}. Hardware, package versions and the pygarble
commit are recorded with the results.

Table~\ref{tab:survey} gives the capture rates. \code{english\_fusion}
flags \respct{english_fusion}{A_capture}\,\% of the junk responses
(\resci{english_fusion}{A_capture}), and the default \code{english}

\respct{lingua}{A_capture}\,\%.

The ordering follows what each method can see. Keyboard mashes and
random letters have improbable character transitions and no dictionary
words, so every method catches most of them. Lingua's near-complete
capture comes from the policy rather than from junk detection: a
short mash is not confidently English, so it is flagged, and
Section~\ref{sec:tweets} shows what that policy costs on real text. The
Markov baseline misses the rows whose transitions happen to be plausible,
such as repeated syllables. The \nAmissedfusion{} rows that
\code{english\_fusion} misses are mostly one to three characters long,
letters mixed with digits, strings with no letters at all, or a short
syllable or punctuation mark repeated; some are real words or short
phrases, which read as English to character and word statistics.

The dataset is used as labelled, and it has some label noise:
\nAmissedall{} rows are flagged by none of the four untuned methods, and
on inspection many are meaningful low-effort answers such as a thanks or
a short positive phrase. The capture rates therefore have a ceiling
below one.

than of recall on realistic junk: its junk is random strings, which share
almost nothing with English, so any character model separates them.

\subsection{Domain-specific tuning}
\label{sec:tuning}

The default \code{english} profile contains two strategies that target
encoding damage: mojibake and control characters. On this dataset they
fire on the \mojibakepct\,\% of tweets that carry mojibake, which the
labels treat as clean, and the control-character check fires on the C1
control codes that the same mis-decoding produces. A user screening
social-media text for gibberish, who does not care about encoding damage,
would remove both. We built that variant, the \code{english} profile
without mojibake and control characters, with the same \code{any} voting
and threshold; the package was not changed. The variant was constructed
after seeing the results above, so it is post hoc and reported as such.

Its results sit in the last row of Tables~\ref{tab:survey}
and~\ref{tab:tweets}. Capture on \SJ{} and recall on \TRS{} are unchanged
at \respct{english_tuned}{A_capture}\,\% and
\respct{english_tuned}{B_recall}\,\%, because no junk row in either
dataset depended on the two encoding checks. The false-positive rate on
tweets falls from \respct{english}{B_fpr}\,\% to
\respct{english_tuned}{B_fpr}\,\%, and precision rises from
\res{english}{B_precision} to \res{english_tuned}{B_precision}. The
point is not this particular variant but the mechanism: a profile is a
list of strategies, each targeting one kind of junk, and a domain that
does not count some kind as junk removes the strategies that target it,
without retraining anything. \code{english\_fusion} contains no encoding
check, so it has no such variant.

\section{Discussion}
\label{sec:discussion}

\paragraph{What the results support.} At default settings pygarble's
\code{english\_fusion} profile captures about nine in ten real survey junk
responses and nearly every random string, while flagging about one tweet
in fifteen, from a one-megabyte install with no dependencies. Neither
baseline matches it on both datasets at once: the Markov baseline flags
far fewer tweets but misses more than a quarter of the survey junk, and
lingua captures almost all junk but flags more tweets and needs a
three-hundred-megabyte install.

\paragraph{Where pygarble is beaten.} The Markov baseline has the lowest
false-positive rate on tweets, \respct{gibberish_detector}{B_fpr}\,\%
against \respct{english_fusion}{B_fpr}\,\%; when wrongly flagging a real
post costs much more than missing junk, it is the better default. Lingua
captures more survey junk, \respct{lingua}{A_capture}\,\% against
\respct{english_fusion}{A_capture}\,\%, under its aggressive policy. The
default \code{english} profile is not suitable for informal text as
shipped: it flags a third of tweets, and still \respct{english_tuned}{B_fpr}\,\%
after the tuning in Section~\ref{sec:tuning}, because its Markov member
alone flags many informal posts.

\paragraph{Guidance.} For screening survey or form free text, use
\code{english\_fusion}; add a minimum-length rule if one- and
two-character answers count as junk. For a new domain, start from a
profile and remove the strategies whose target the domain does not treat
as junk, as in Section~\ref{sec:tuning}. When false positives are costly,
prefer the Markov baseline at default settings, or measure a threshold on
labelled rows of your own data. For multilingual input, route by language
first; a language identifier answers that question, and it is not a junk
detector.

\section{Limitations}
\label{sec:limitations}

Two public datasets are measured, both English and both short text; the
behaviour on long documents is not measured. \SJ{} has only junk, so it
measures capture and nothing about false positives; \TRS{} has random
strings as its only junk, which are easier than real junk. There are two
baselines and no neural one. Each method is run once at its default
decision, so the results say how the tools behave out of the box, not how
well they can be tuned; the one tuned variant is post hoc and was chosen
with knowledge of the tweets results. A comparison at a matched
false-positive rate, with thresholds fitted on a development split, was
computed in an earlier version of the protocol and removed from the
paper's scope; in it the Markov baseline captured more survey junk than
\code{english\_fusion}. It remains in the repository history.

\section{Reproducibility}
\label{sec:repro}

The benchmark code, the frozen protocol with its dated deviations file,
and the results are in the repository under \code{paper/}. The manifest
records the SHA-256 hash of each raw file (for \SJ{}, beginning
\code{\shaA}) and every row id; no dataset text is committed. Per-row
scores and decisions for every method are committed, so every number in
this paper can be recomputed without the raw data:
\begin{small}
\begin{verbatim}
make benchmark-verify PYTHON=<venv>/bin/python
make preprint PYTHON=<venv>/bin/python
\end{verbatim}
\end{small}
The first command recomputes the metrics from the saved predictions and
fails on any difference. The second regenerates the figure, the tables
and the number macros this paper is typeset from, then builds the PDF.
Re-scoring from the raw files is described in the benchmark README;
scores are deterministic.
